# 桌面自动更新发布

桌面自动更新只替换应用本身。项目、素材、设置、BeefAPI 登录和自定义插件留在用户数据目录。更新源是 GitHub Release 上的签名清单，不经过业务云接口。

qisiTV 没有默认更新源，也不会从上游 BeefTV 下载替换程序。发布方必须显式配置自己的 `QISITV_UPDATER_FEED_URL` 和 `QISITV_UPDATER_PUBLIC_KEY`；未配置时更新器关闭。下文地址是占位示例，不代表已有公开发行仓库。

`v1.5.2` 及以前的安装包没有更新器。给仓库补上清单，不会让已经装好的程序自己升级。用户需要先手动安装第一个带更新器的版本。

## 用户侧行为

带更新器的应用会显示当前版本，并在启动时检查一次更新。用户点击后才会下载；下载完成不会自动退出。只有用户选择安装后，应用才会保存当前工作、退出并启动新版本。保存失败会留在当前应用中。

浏览器构建不会请求更新源。

## 数据保留

| 系统 | 更新包内容 | 数据目录（不会进包、不会被替换） |
| --- | --- | --- |
| macOS | `qisiTV.app` | `~/Library/Application Support/qisiTV` |
| Windows | `qisiTV.exe` 与 `plugin-packages/*.qisitv-plugin` | `%AppData%\qisiTV` |

应用包身份和可执行文件路径保持稳定，前端 IndexedDB 可以继续用。官方插件随应用包更新；装在数据目录里的自定义插件会留下来。打包时遇到 `.env`、数据库或用户数据目录会失败。

## 两种签名

更新签名和 Apple 签名是分开的。

更新清单用 Go 标准库 Ed25519。信封是：

```json
{
  "payload": "BASE64_EXACT_JSON_BYTES",
  "signature": "BASE64_ED25519_SIGNATURE_OF_PAYLOAD_BYTES"
}
```

签名对象是 payload 的原始 JSON 字节，不是 Base64 文本。验签后再读：

```json
{
  "schema": 1,
  "version": "vX.Y.Z",
  "commit": "完整 Git SHA",
  "notes": "发行说明",
  "platforms": {
    "darwin-arm64": {
      "url": "https://releases.example.com/qisitv/qisiTV-vX.Y.Z-darwin-arm64.zip",
      "sha256": "hex",
      "size": 123
    }
  }
}
```

平台键为 `darwin-arm64`、`darwin-amd64`、`windows-amd64`。版本只接受稳定的 `vMAJOR.MINOR.PATCH`。应用会拒绝相同或更低的版本。

Apple ad hoc / Developer ID / 公证只影响 Gatekeeper。现有 macOS 发布脚本仍使用 ad hoc 签名。没有 Apple 证书也可以做自动更新。Windows 构建需要支持 DWARF 5 的 UCRT64 GCC（binutils 2.37 或更新），见 `scripts/assert-windows-dwarf5-cgo.ps1`。

## 密钥

在本机生成到明确文件，权限 `0600`，不要把私钥打到终端或提交进仓库：

```bash
cd backend
go run ./cmd/update-release gen-key \
  --private-key /path/to/qisitv-updater.private \
  --public-key /path/to/qisitv-updater.public
```

| GitHub 位置 | 名称 | 内容 |
| --- | --- | --- |
| Actions secret | `QISITV_UPDATER_PRIVATE_KEY` | 64 字节私钥的标准 Base64 |
| Actions variable | `QISITV_UPDATER_PUBLIC_KEY` | 32 字节公钥的标准 Base64 |

发布前会核对私钥推导出的公钥与变量一致。缺密钥或对不上都会失败，不会发布未签名更新源。

私钥丢失后，已发出的包仍只认旧公钥。换密钥必须再发一个需要手动安装的引导包。私钥泄露时停止用旧密钥签名，换新密钥并请用户手动安装新包。

生产密钥由仓库负责人保管。本仓库的工具不会生成生产密钥，也不会改 `VERSION`。

## 发布流水线

在发布方自己的 qisiTV 仓库 `main` 上手动运行 `Release desktop`。`confirm_version` 必须等于 `VERSION`。`CHANGELOG.md` 里对应的 `## vX.Y.Z` 会同时成为 GitHub Release 说明和清单 `notes`。

工作流默认只读；仅创建草稿和最终发布的任务申请 `contents: write`。构建任务不持有发布写权限或签名私钥。步骤：

1. 校验稳定版本、唯一 tag、密钥和 changelog。
2. 创建 **draft** Release。
3. 用现有脚本构建 macOS arm64、macOS amd64、Windows amd64，并注入 FeedURL 与公钥。
4. 按固定文件名打包 zip 并保存为 Actions 构建产物。
5. 三个包都齐了之后才签名 `desktop-update.json`。
6. 把所有包和清单上传到 draft 后，发布并明确标记为 latest。此时更新源才指向这个完整版本。

固定文件名：

```text
qisiTV-vX.Y.Z-darwin-arm64.zip
qisiTV-vX.Y.Z-darwin-amd64.zip
qisiTV-vX.Y.Z-windows-amd64.zip
desktop-update.json
```

同一版本的资源不可改写。已存在的 tag 或 Release（包括 draft）会让工作流失败。失败且从未公开的 draft，确认无人可下载后才能删除 draft 和 tag，再对同一版本重试。

本地脚本、数据目录和打包命令写在仓库 `docs/desktop-release.md`。

```bash
cd backend
go test ./cmd/update-release
go run ./cmd/update-release package --platform windows-amd64 --input cmd/desktop/build/bin --output /tmp/qisiTV-vX.Y.Z-windows-amd64.zip
```

## 回滚

不要覆盖或删除已经发布的 zip 和清单。要收回有问题的版本，发布一个更高的稳定号。已经更新成功的用户，不会因为删除 GitHub Release 而回到旧包。

流水线显式标记 latest，且拒绝非递增稳定版本。不要手动把旧版本标记为 latest。

客户端在退出前重新验包，并在程序所在磁盘准备安装文件。数据目录和程序目录重叠时会拒绝安装，避免覆盖自定义插件。替换只使用同磁盘重命名，安装锁防止多个实例同时替换。安装或进程启动失败时尝试恢复旧程序；若应用未退出、安装程序已经停止，界面会恢复可重试状态。成功启动后仍保留程序旁 `.qisitv-update-*` 目录中的备份和恢复记录；确认新版本正常后可清理该次目录。

启动了进程不等于 SQLite 迁移或界面正常，因此不会在新进程启动后自动降级。恢复旧程序前需确认数据库兼容，必要时使用匹配的数据备份。此更新器不会复制或还原全部用户素材。
